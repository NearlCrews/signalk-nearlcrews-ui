# API reference

This reference summarizes the public `0.12.x` API. The TypeScript declarations shipped with the package are the canonical source for complete native HTML and React Aria prop types. This document focuses on package-specific props, defaults, entry points, ref targets, and user-visible strings. Every error the package throws starts with `signalk-nearlcrews-ui:` and a space, so an error that escapes a panel into Signal K Admin's error boundary names the package; development warnings are separate and never run in production.

Focused-entry-point APIs are not also exported from the package root, with one deliberate exception: `/format` republishes helpers the root also exports, because its whole purpose is reaching them without React in the graph. Consumers bundle each JavaScript entry point they import into their remote. Webpack consumers share only React and React DOM with the Signal K Admin host; Vite and other ESM consumers resolve the React entry points through the host-global shims instead. Every JavaScript entry declares a `default` condition pointing at the same target as its `import` (or, for `/federation`, its `require`) condition, so CommonJS tooling on Node 22.12 or newer can `require` it as well. `/host-harness` belongs in a consumer's browser test fixture and never in a panel: `snui-check-consumer` fails a remote that contains it.

The stylesheet entry point has no React import or execution requirement. Installing the package still resolves the package's declared dependencies and React peer dependencies; `tokens.css` is an entry point, not a separate dependency-free package.

### Entry point sizes

The last row measures what a panel remote actually pays: `fixtures/size/consumer-panel.ts` imports every name at least five of the six NearlCrews panels import, and the check bundles it the way a remote is built, with tree shaking, so it counts only the components those names reach. Adding up the entry rows a panel imports overstates the result: each row is measured with every one of that entry's components live, and a focused entry carries the style modules of components a given panel never renders, plus install machinery the root entry already brought.

`PanelShell` is the frame every configuration panel repeats: it runs the `supportsNativeCssScope` preflight once at mount and renders `UnsupportedBrowserNotice` (or the `unsupported` element) when it fails, otherwise `PanelRoot`, an outer `Stack`, one polite and one assertive live region for the whole panel, the optional title at `headingLevel`, the optional `description`, which renders with or without a title, the `ThemeToggle` where `themeToggle` places it, and a `PanelErrorBoundary` around the children. Above a configuration panel Signal K Admin renders one heading, the plugin card header, an `h5` holding the npm package name, and no `h1` at all, so level 2 is the highest a panel should take and the one that keeps its sections reachable by heading level. The card header already names the plugin, so most panels pass no `title`: a panel title adds a second name for the same plugin. The two regions the shell mounts are what `usePanelAnnouncer` writes to, so a panel announces through a region that existed before the message. Both carry the marker React Aria spares when a `Dialog`, `AlertDialog`, `Menu`, or modal `Popover` hides the rest of the page, so an announcement made while an overlay is open is heard. Each message is a node of its own that leaves after 7 seconds: two messages from one handler are both read, a repeat of the same words is announced again, a blank message is ignored, and a message sent in the regions' first 100 milliseconds waits for them to exist. A titled shell also offers the level below its title to the `Section` and `CollapsibleSection` rendered inside it, so a panel titled at level 2 heads its sections at level 3 without being told; a shell with no title heads nothing and passes its own level through, an explicit `headingLevel` on a section still decides, and the derived level stops at 6. `themeToggle="between"` places the selector after the title block, so a panel with no title has nothing for it to sit between and takes the default `"end"` instead; leading the panel would hand the theme selector the panel's first tab stop, which no placement describes. A configuration panel states the placement rather than leaning on the default: `themeToggle="end"` is the convention the design contract records, and `themeToggle="none"` with a hand-placed `ThemeToggle` is the deliberate way out of it. On an unsupported browser the shell forwards its `className`, `id`, and other attributes to the notice, whose heading and explanation come from `labels.unsupportedBrowser`: the shell reads that group from its own `labels` prop, because the notice renders before any panel exists to publish the bundle. When the host's React is below the floor rather than the browser, the notice is headed "Signal K update required" and names both versions in English, since browser advice would send the operator after the wrong update. The panel `ref` is not forwarded to the notice, because that branch renders a section rather than the panel div. `PanelErrorBoundary` catches a render error inside the panel and offers "Try again", which clears the error and renders the children again, plus a reload action, which `PanelShell` offers by default and `onReload={null}` withholds. The explanation under the fallback's title names only the actions on screen: `description` with Try again alone, and `reloadDescription` when the reload is offered too. The default fallback is not an assertive alert: it takes focus when the crash left the page with nothing focused, and otherwise announces through the panel announcer. Its heading takes the level below the section a boundary sits in, or below the title of a `Dialog` or `AlertDialog` it sits in, like any heading inside one. The boundary records every caught error with `console.error`, including the component stack, as well as calling `onError`. Render it inside `PanelRoot` so the fallback is styled.

`Section.leading` and `CollapsibleSection.leading` render before the heading, outside the heading and outside the toggle button, so the content is not part of the section's name and keeps its own semantics and hit area: an enable checkbox stays a checkbox, and a decorative glyph takes `aria-hidden` from the consumer. `variant="embedded"` drops the border, radius, and shadow for a section nested inside a `Card`. A section is a named region landmark unless its context says otherwise: `landmark` defaults to `false` for `variant="embedded"` and for a section nested inside another package region (a `Section`, `CollapsibleSection`, or `InlineConfirm` that is itself a landmark), and `Accordion` applies the same default to its children, because a region per nested row crowds the list a reader navigates by. An explicit `landmark` always decides, so a child can opt back in. A `Dialog` or `Popover` starts a fresh outline, because it is portaled out of the section it was opened from: the sections inside it are not nested in that section. A dialog's title heads the dialog the way a shell title heads the panel, so the sections inside take the level below it and size as top sections, and a confirmation directly inside nests below the title too; a popover has no title, so its sections take the level of the place it opens from: the shell level, or inside a dialog the level below the dialog's title. `landmark={false}` removes the region naming, including any `aria-labelledby` the consumer passed, and the section is then named by its heading in the ordinary way.

`InlineConfirm.busy` blocks Confirm while the confirmed action runs. It does not close the region's escape path: Cancel stays enabled and Escape keeps dismissing, because a user declining an action is not in conflict with work already under way, and a keyboard user must always be able to leave. So `onCancel` can fire while `busy` is true, with reason `"cancel"` or `"escape"`, and the consumer decides whether that aborts the work, closes the region, or both. `busy` takes effect only on a controlled region: an uncontrolled one closes itself on Confirm, so there is nothing left on screen to block. `onOpenChange` reports every close in one place. The title's level defaults to the one below the `Section` or `CollapsibleSection` that contains the confirmation, or below the title of a `Dialog` or `AlertDialog` it sits in, and otherwise to the level a section in the same place would take: below a `PanelShell` title, else 2. An explicit `headingLevel` decides, and a derived level stops at 6.

`statusRef`, `initialFocusRef`, `returnFocusRef`, and `dismissFocusRef` are focus destinations. They are not aliases for a component's own `ref`. `Banner.dismissFocusRef` serves every way the banner takes focus away, not the Dismiss press alone: an action in `actions` that unmounts the banner, and an announcing banner whose actions go with its message, both hand focus to the same destination. The banner moves focus only when it held it, and the move is synchronous, so a panel that focuses whatever it renders in the banner's place keeps that focus. `ActionBar` makes its status destination programmatically focusable but does not move focus automatically; the consumer calls `statusRef.current?.focus()` after the initiating control disappears or becomes unavailable. A viewport-bottom bar scrolls a focused panel control clear when focus moves or a viewport resize docks the bar, preserving focus-ring clearance through nested scroll containers. It never scrolls while a pointer is pressed, so a press on a control the bar overlaps keeps its click, and a clearance skipped for that reason is not replayed afterward: a pointer user can see the control they pressed, and a later scroll would move content under a pointer that may still be there. Keyboard and programmatic focus clear immediately. The bar docks only while its anchor lies below the docking edge, and keeps its height in flow while docked, so a docked bar that is a panel's last child is back in flow above whatever follows it at maximum scroll: the theme selector at the foot of a `PanelShell` stays reachable in a host that scrolls the document, as Signal K Admin does, and needs no clearance padding.

#### CollapsibleSection mountStrategy and effects

`mountStrategy` decides what happens to hidden content, and the two retaining values have consequences a consumer must design for.

- `"retain"`, the default, and `"lazy-retain"` keep hidden content mounted inside React `Activity`. State and `useRef` values survive a collapse, and so does uncontrolled DOM value state. Every effect and layout effect in that subtree runs its cleanup when the section collapses, refs detach, and all of them run again when it reopens.
- `"unmount"` removes hidden content. Effects unmount for real and state is discarded, so nothing survives a collapse.

The consequence that surprises consumers is that an effect with an empty dependency list is not a run-once effect under a retaining strategy. It runs once per expand, against state that survived from the previous expand. Guard genuinely one-time work with a `useRef` flag, which survives the collapse with the state it protects.

Two failure shapes follow from the same rule, both observed in consumer panels:

- A field that reports validity from an effect, and clears that report in the effect's cleanup, silently drops its invalid state when the section collapses. Re-running the effect on expand then reinitializes the field from props and discards an edit the user had in progress, because the edit survived but the effect treated the expand as a fresh mount.
- A request that starts in an effect and aborts in that effect's cleanup is aborted when the section collapses, so the completion path that would clear a busy flag never runs and a control stays `aria-busy` forever.

Keep each cleanup symmetric with its own setup: unsubscribe what the effect subscribed, and do not use a cleanup to mutate reported validity, busy state, or other state that must outlive the hidden period. Initialize from props only behind a ref guard. An effect-registered listener also observes nothing while the section is collapsed, so a subtree that must see events during that time, a form reset for example, belongs outside the collapsible or in a consumer-owned store. Choose `"unmount"` when a subtree cannot tolerate paused effects and its state is disposable, and keep a retaining strategy when the state must survive.

A control inside a closed section cannot take focus until the section's reveal commits. To send focus to one, open its ancestors inside `flushSync` so the reveal commits synchronously, then call `revealAndFocus` on the control's ref or on the section's `triggerRef.current`, rather than waiting a counted number of animation frames or querying the package's markup. The migration guide carries the recipe.

`TextInput` accepts `date`, `datetime-local`, `email`, `month`, `password`, `search`, `tel`, `text`, `time`, `url`, and `week`. `Textarea` keeps the HTML element's casing rather than `TextArea`. `monospace` renders a text control in the panel's monospace stack for keys, paths, and identifiers; `Textarea.minRows` sets the visible row floor in place of the default minimum height and, where the browser sizes fields from content, lets the control grow from that floor. `Button` makes empty, dangerous, and unknown anchor schemes inert while keeping `role="link"`, and logs one development warning per rejected `href`. HTTP, HTTPS, mail, telephone, fragment, query, and relative destinations remain active.

`Button.ariaDisabled`, when set, decides whether activation is blocked and a native `aria-disabled` attribute is ignored; when it is omitted the native attribute is read. A natively `disabled` button never also carries `aria-disabled`: the two are exclusive, and `disabled` wins.

A blocked button with no reason is unfinished, because a keyboard user who lands on it and presses it hears nothing change and nothing explained. Development says so once for a button blocked with `ariaDisabled` that carries neither `disabledReason` nor an `aria-describedby`, and once for a `disabledReason` beside native `disabled`, which takes the button out of the tab order and so drops the reason. A blocked `CheckboxGroup` or `SegmentedControl` option with no reason is reported the same way, with the fix "Pass disabledReason on the option." A block that lasts only while another action runs needs a reason too, such as "Available when the scan finishes"; a `loading` button's own busy description is its reason. Pass the reason one way, never both: text wired by hand through `aria-describedby` is read already, so repeating it in `disabledReason` reads it twice. `disabledReasonVisibility="hidden"` serves assistive technology only, which leaves a sighted keyboard or touch user with nothing to see; `"visible"` draws the reason as a muted line under the button and wires it once, as the button's description. The button then renders inside a wrapper that is present whenever the prop is set, so the button stays the same element, and keeps focus, as it blocks and unblocks.

Give a button that needs more context than its visible words that context as a visually hidden suffix, `Remove<VisuallyHidden> {path}</VisuallyHidden>`, rather than as an `aria-label`: its accessible name then still contains the word on screen, which is what a speech input user says. Development warns once when a button whose children are plain text carries an `aria-label` that does not contain that text.

`Checkbox.ariaDisabled` follows the same rule and applies it to a value rather than an action. Reach for it where the box cannot change right now but its value is real, such as the last remaining selection in a list: `disabled` takes the box out of the tab order, so setting it on the box the user is standing on destroys their focus and drops them on the body. A blocked box stays focusable, keeps its checked and mixed states, and still submits with its form, while the change is refused from the box, from the label, and from the Space key alike. `Enter` is left alone, because it belongs to the surrounding form rather than to the box. Its `disabledReason` is read after its description while the block holds, and the development warning for a reason-less block applies to it as it does to a button. `CheckboxGroup` takes the same flag and reason per option, and select-all leaves blocked options as it finds them, since an option the user cannot change is not one select-all may change for them. `Switch` and `RadioGroup` express this as `readOnly`, which React Aria implements: the control keeps its tab stop and refuses the change. Reach for `disabled` on any of them only when the control is genuinely unavailable, where giving up the tab stop is part of what you are saying.

An intrinsic `LabeledField` child must be a labelable `button`, non-hidden `input`, `meter`, `output`, `progress`, `select`, or `textarea`. Use the render-prop form for a composite control. Children must forward `id`, `required`, `disabled`, `name`, `aria-describedby`, `aria-errormessage`, and `aria-invalid`. `FieldControlProps` and `LabeledFieldControlProps` name this contract. The render-prop argument also carries `descriptionId` and `errorId`, which are lookups rather than attributes: pass it through `splitLabeledFieldControlProps(props)` to receive `{ controlProps, descriptionId, errorId }`, spread `controlProps` onto the control, and point secondary controls at the ids with `aria-describedby`. The package's own text controls, `RangeInput`, and `Select` drop the two lookups if the whole argument is spread onto them, so no stray attribute reaches the element, but a control of your own does not. Where text outside the field also describes the control, name it in `controlDescribedBy`, which takes one id or a list: the field reads its own description and error first and those ids after, and both the element-child and the render-prop form receive one merged `aria-describedby`, so no caller writes the join.

`NumberField` keeps the text the user is typing in a draft and commits numbers. Without `fallback` it validates: an empty, unparsable, fractional (under `integer`), or out-of-range draft commits nothing until the user fixes it, and reports `onValidityChange(false)` on the keystroke that makes it invalid; `exclusiveMin` and `exclusiveMax` make the bound itself invalid, and `step` reaches the input for its spinner without being enforced, so a half-typed value is never rejected mid-edit. The message and `aria-invalid` appear once the edit finishes, on blur or Enter, and clear on the keystroke that makes the draft valid, so an operator replacing a value is not told it is wrong halfway through typing it. A save that blurs the field finishes the edit too, so a refused save shows the message. With `fallback` it clamps: empty or unparsable input commits the fallback, fractions truncate, values snap to `step`, and out-of-range values clamp to the nearest bound, so every keystroke commits a number. `allowEmpty` widens `value` and `onValueChange` to admit `undefined` for a cleared field. Blur and Enter finish an edit (an invalid draft stays visible with its message), a wheel over the focused input blurs it so scrolling cannot spin the value, and the draft survives a retaining `CollapsibleSection` collapse. `onValidityChange` fires on transitions only and never from an unmount, so a consumer that stops rendering a field clears its own entry. A `useResetDrafts` reset also reports a field valid that left the tree while invalid, so keep bookkeeping a repeated report cannot unbalance, such as a set of names. `useNumberDraft(value, onValueChange, options)` exposes the same behavior for a bare `NumberInput`: its `valid` reports the state on every keystroke, crossing exactly when `onValidityChange` does, while `invalidReason` and the input's `aria-invalid` wait for the edit to finish. `resolveNumberDraft(raw, options)` is the pure resolution step, which reads only the notation an `<input type="number">` can produce.

A draft that never committed is typed against the value the panel still holds, so a Discard that restores that value changes nothing the draft is keyed on. Call `useResetDrafts()` from the panel's Discard handler: it drops every draft in the panel, including an invalid one inside a collapsed section, and a field whose draft was invalid reports itself valid again. `PanelRoot` and `PanelShell` publish the reset, and an explicit `resetKey` still combines with it.

`NumberField.messages` replaces the message for a reason, keyed by `NumberDraftInvalidReason`. A text message may carry `{min}` and `{max}`, which the field fills with its bounds printed the way the input accepts them back; a node renders as written; and a function receives a `NumberFieldMessageContext`, with the reason, `min`, `max`, `exclusiveMin`, `exclusiveMax`, `integer`, and the field's `unit`, and returns the message, for one that names what the field measures. The `numberField` bundle group takes text only, with the same placeholders.

`NumberField.unit`, `RangeInput.unit`, and `Metric.unit` take content, or a `NamedUnit`, `{ symbol, name }`: the symbol is drawn and hidden from assistive technology, and the name is read in its place, with a leading space so `Metric` reads "12 knots" as one phrase. On `NumberField` the unit is read as part of the input's description, never its name, so a speech input user still says the label; on `RangeInput` it becomes the slider's `aria-valuetext`, which follows the value, and an `aria-valuetext` the caller passes wins. A blank name leaves the symbol to be read as it is. A unit is a label, not a conversion: the next section says where it comes from.

Every control and group takes its accessible name from `label`: `Checkbox`, `Switch`, `Radio`, `RadioGroup`, `SegmentedControl`, `ThemeToggle`, and `NumberField` through `LabeledField`. `Switch` and `Radio` also accept children as the label. `FieldGroup` and `CheckboxGroup` render a real `<legend>` and take `label` and `legend` alike, both permanently, so a consumer can reach for one word everywhere or for the element's own; when a group receives both, `label` names it, and a group with neither throws "FieldGroup requires a non-empty label or legend." (or the `CheckboxGroup` equivalent). `SegmentedControl` and `ThemeToggle` render a `role="radiogroup"` div and take `label` only, which `SegmentedControlProps` requires. The rule for a label's type follows from what the label becomes: plain text where the value turns into an accessible name, `ReactNode` where it is only rendered, and both on `Menu`, whose trigger derives a name from its content when `triggerLabel` is absent. `Checkbox.labelVisibility="hidden"` keeps the required label in the accessible name while removing it from the layout, for a select-all box in a table header or a toggle in a dense row. `SwitchProps` and `RadioProps` are unions over the naming pair: omitting both `label` and children is a type error, while a present but blank value still throws at render.

Change handlers split along one rule. Native wrappers (`TextInput`, `NumberInput`, `RangeInput`, `Select`, `Textarea`, and `Checkbox`) take React change events through `onChange`. Composed controls report values with a callback named for the payload: `Switch.onCheckedChange(checked)`, `RadioGroup.onValueChange(value)`, `SegmentedControl.onValueChange(value)`, `ThemeToggle.onValueChange(theme)`, `CheckboxGroup.onValueChange(values)`, and `NumberField.onValueChange(value)`.

`SegmentedControl.options` must contain at least one option. Every option needs a non-empty label, and option values must be unique. All four arrow keys move within the group in either orientation, the horizontal pair mirroring in a right-to-left panel, Home and End reach the ends, and holding Ctrl, or Command on macOS, moves focus without changing the selection. `readOnly` marks the group `aria-readonly` and refuses every change without marking the options unavailable, the way `RadioGroup` reports it, so the operator hears a fixed value rather than a broken control. A per-option `ariaDisabled` refuses that option through `aria-disabled`: a press changes nothing, and an arrow key reaches it without selecting it, so the next arrow selects past it. Neither takes an option out of the tab order, so the option the operator is standing on keeps its focus. An option's `disabledReason` is read as its description while it is blocked and dropped once it is live, and development says so once for a blocked option without one. `dataAttributes` puts `data-*` attributes, written in full, on an option's radio, a hook that does not depend on the option's wording. Names beginning `data-snui-` are the package's own test hooks, so a panel picks names of its own.

### Units

The package draws and speaks a unit; it never fetches, selects, or converts one. A panel that shows a length, depth, speed, or temperature follows the Signal K server's unit preferences rather than a panel-local switch or a guess from the browser locale, and resolves them in four steps:

1. Read the user's own choice from `GET /signalk/v1/applicationData/user/unitpreferences/1.0.0` with same-origin credentials. It holds only `{ activePreset }`.
2. Resolve that name with `GET /signalk/v1/unitpreferences/presets/{name}`.
3. Without a user choice, read the server-wide preset from `GET /signalk/v1/unitpreferences/active`, which needs no authentication and carries each category's `targetUnit`, `formula`, `inverseFormula`, and `symbol`.
4. On any failure, use metric: servers without the unit preferences API answer 404.

The server's own per-user resolution has one more step, a legacy `userPresets` configuration a panel cannot read, so the ladder above is the closest a panel gets. A value read from a Signal K path takes its display unit from that path's metadata, whose `displayUnits` the server has already resolved for the user, rather than from the category preset. Keep configuration and the data model in SI and convert only at the field. For a `NamedUnit`, the symbol comes from the preset and the long name from `GET /signalk/v1/unitpreferences/definitions`, where each conversion carries a `longName` such as "knots" beside the symbol "kn". The lookup, the conversion, and the fallback all stay in the plugin.

`Stack`, `Cluster`, `Card`, `MetricGrid`, `Text`, `Code`, and `VisuallyHidden` type their props by the element `as` names: `<Stack as="form">` accepts form attributes and its `ref` resolves to the form element. A computed `as` covering the whole element union falls back to the attributes every HTML element shares. `Stack divided` draws `--snui-color-border-subtle` between its items; an item the page hides, or a visually hidden one such as a `LiveRegion`, draws no rule and takes none. For rows inside a card, put the stack in a `Card` with `density="flush"`.

Every tone-badged component (`Badge`, `Metric`, `Banner`, `StatusIndicator`, `Card`, `CollapsibleSection`, `Progress`, `FreshnessNote`, toasts, and field errors) renders the same tone glyph and visually hidden announcement for a semantic tone, so the state never depends on color alone. The glyph takes a shape per tone, the info, warning, and danger shapes the status dots use: info in a rounded square, warning in a triangle, and danger in a hexagon. Success is a heavy check with no enclosure, where the success dot is a diamond. The shapes survive forced colors. A blank `toneLabel` falls back to the default tone name on every one of them, and a `toneLabel` on `tone="neutral"` is ignored everywhere, because neutral carries no meaning to announce. `StatusIndicator` shows the glyph beside its shaped dot, and `size="compact"` keeps only the dot and glyph visible while the text stays in the accessibility tree; with `settleMs`, the region inside speaks the compact text once it settles, and nothing carries it while the region waits. A `Card` with a semantic `tone` paints the Banner accent bar and places the glyph in its header; give a toned card a header so the glyph has a home. Night collapses the tone colors onto one red-capped hue, so a `Progress.tone` or a `Text.tone` there reads as emphasis rather than as a particular tone: state the meaning in words wherever it matters. A `Badge` is a label, not a control; a count the operator can act on belongs in a compact `Button`, in the danger variant when the action is destructive.

`live` on `Banner`, `StatusIndicator`, and `Metric` makes the component announce its own updates, and a live region has to exist before its first message or a screen reader does not observe it. So render the component wherever the panel can produce a message and let its content go empty: `<Banner live="polite">{message}</Banner>`, not `{message && <Banner live="polite">{message}</Banner>}`, which builds the region and its first message in the same commit. The components also guard that case themselves: a polite one that mounts with content holds it for 100 milliseconds, so the region exists empty first and the message is then announced, while a `Banner` keeps its actions on screen throughout. Pass `deferFirstMessage={false}` where the content at mount is not news, such as a status line present when the panel loads. An assertive region, which screen readers announce on insertion, is not held unless `deferFirstMessage` asks, so a failure does not appear late. With `live` set, or a live `role` given to `Banner` or `StatusIndicator`, and nothing to show, the component renders the element that carries the role empty, with no tone glyph, no dot, and no unit, and the stylesheet takes that empty element out of the flow: it reserves no box, border, padding, or margin, so a waiting region is invisible. A `Banner` carrying `actions` or `onDismiss` always renders in full, because hiding a focusable control would strand it. The same rule governs the field error regions and `LiveRegion` below. `live` defaults to `"off"` on `Banner`, `StatusIndicator`, and `Metric`, and to `"polite"` on `LiveRegion`, whose whole job is announcing. A role that announces by itself, `alert`, `log`, or `status`, suppresses `aria-live` so nothing double speaks; any other role, a landmark or a grouping, keeps the mode the caller asked for.

`settleMs` on `LiveRegion`, `StatusIndicator`, and `Metric` speaks a changed message only once it has stayed the same for that many milliseconds, and every change restarts the wait, so a match count beside a search field is announced once, after the typing stops, rather than once per key. The message a component mounts with is exposed at once. On `LiveRegion` the region is empty while it waits. On `StatusIndicator` and `Metric` the visible text still changes at once: the visible parts step out of the accessibility tree, and a visually hidden region inside the component speaks the tone and text once they settle, so the component element itself no longer carries the live role. Anything but a positive number exposes every change at once.

`LiveRegion` is a visually hidden announcer for state changes no visible control owns, such as a scan result count. Render it before the first message and update `message`; screen readers only observe a region that already existed. `deferFirstMessage` is for the region that mounts together with its subject, a panel switching to a mode that renders both: it holds the first message for one beat so the region exists empty first. Left `false`, the default, a message present at mount renders at once, which is right for a region mounted with the panel, before anything has happened. Setting `message` to the words the region already carries changes nothing in the DOM and is therefore silent, so pass an `announceKey` that differs per announcement (a press count, or the id of the event behind it): the region empties itself for a tenth of a second and restores the text, which is the change a screen reader reads. Callers pass plain text and never an invisible character. `RelativeAge` renders an age as words: pass `since` for a live age the component keeps current (it ticks every `tickMs`, stamps a `<time dateTime>` from the timestamp, and reads the clock at mount, on its tick, and once more in the render that first sees a new `since`, so a moment stamped at receipt is never measured against an older reading; that reading is stored with the moment, so every later render of it is pure). Every age sharing a `tickMs` shares one timer and refreshes at the same instants, so a panel full of ages costs one wake-up per interval. Pass `ageMs` instead for a value the consumer already computed. Prefer the component wherever the result is rendered rather than concatenated: `.snui-relative-age` carries tabular numerals, so `<RelativeAge ageMs={n} options={RELATIVE_AGE_NARROW} />` holds its width as the digits change, while the bare string `formatRelativeAge` returns carries no class and reflows on every tick. `announceKey` on `Banner` and `StatusIndicator` works the same way as it does here.

`FreshnessNote` says how old a polled status is, as one line: a muted "Checked 2 minutes ago" while the reading is current, "Out of date: updated 6 minutes ago" in the warning tone with the warning glyph once it is stale, so staleness never rests on color alone, and "Not checked yet" before the first sample. A sample stamped more than a minute ahead of the browser's clock has no age to state, so the note reads "Checked at an unknown time" while current and "Out of date: last update time unknown" while stale. Under `options.negative: "fallback"`, a sample any amount ahead of the clock takes the same wording, because `RelativeAge` would print its fallback. The stale wording is its own rather than "Checked", which on a stale readout reads as reassurance. The consumer keeps the threshold: pass the `stale` that `usePollFreshness` reports, measured with the same `tickMs`, and a `since` taken from the browser's clock when the sample arrived. The age ticks, so the note is not a live region; the panel announcer says the turn to stale once, "Status is out of date.", and the recovery once, "Status is current again.", and nothing for the state the note mounts in. Both announcements need a `PanelShell` around the note. `labels` replaces the wording for one note, and the bundle's `freshnessNote` group for the whole panel; `fresh` and `stale` mark where the age goes with `{age}`, which a translation may move, and a wording without it shows no age.

In normal component use, `ThemeToggle` renders inside `PanelRoot`. An advanced integration may supply the exported `ThemeProvider` directly and read the current choice with `usePanelTheme`, but that provider does not install component styles or create an overlay portal root. Both `ThemeProvider` and `PanelRoot` take `defaultTheme`, the choice a document with no stored preference starts on; there is no controlled `theme` prop, because the preference is one document-wide value. `ThemeToggle.choices` is the set of themes offered and `choiceLabels` the names each choice shows, keyed by `ThemeChoice` the same way in the bundle's `themeToggle.choiceLabels`. `UnsupportedBrowserNotice` is intentionally standalone so a consumer can render it after a failed browser preflight without first mounting `PanelRoot`; `PanelShell` does that for you. The notice is a plain section named by its heading, not a live region: it is present at first render, so there is nothing to interrupt. It carries `data-snui-unsupported` and `data-browser-compatibility-message` on its root, the two public hooks a host or a browser test selects it by, and it joins a consumer `aria-labelledby` with its own heading rather than replacing it.

Save is enabled while there is something to save (edits, or a plugin that has never been configured) and blocked by `invalidMessage` or `saving`; the status is a polite `StatusIndicator` whose tone follows the state, including a validation message, so the region keeps one stable role rather than gaining it in the same commit that writes the text. While `invalidMessage` blocks a save, Discard stays available even with nothing dirty, because an invalid draft never commits: the panel calls `useResetDrafts()` from `onDiscard` to throw that draft away. A save the bar has to refuse is blocked through `aria-disabled` and a description rather than the native `disabled` attribute, so Save and Discard keep their place in the tab order and say why; `SaveActionBarState.blocked` reports that state to a consumer deriving it. `resolveSaveActionBarState` exposes the same rules as data. Pair the bar with `useUnsavedChangesGuard(dirty)`, which asks the browser to confirm unloading while `dirty` is true.

Focus moves once, after `onSave` or `onDiscard` has run, because the pressed button usually disables itself. A handler that knows where the reader should go returns that place, an element or a ref (a `SaveActionBarFocusTarget`), and the bar sends focus there: a panel that validates on submit returns `validity.firstInvalid()` from `useFieldValidity`, the first invalid field on screen. A handler that returns nothing leaves the bar's own rule in charge: the status takes focus under `focusOnAction="status"`, the default, and nothing moves under `"none"`. A target that cannot take focus, a detached element or a ref with no current value, falls back to that rule, and a returned target wins over `"none"`. Only a target returned synchronously is followed: the bar does not await a returned promise, so an async handler gets the status, or no move under `"none"`. The status takes focus only from the pressed button or from the page body, so a handler that moved focus itself keeps its destination.

`outcome` reports what the panel heard back about its last save, a `message` and a `tone` it computed from the server's answer, in the bar's own status instead of a second banner beside it. The bar only presents it: the request, its timing, and any retry stay with the panel, which clears the outcome when it starts the next request. A `"danger"` outcome keeps Save available for a retry even with nothing dirty, and stays through later edits, because the configuration on the server is still not the one requested. Any other tone reports an accepted request in place of the saved message and gives way to the next edit. The status stays polite for an outcome too: the operator pressed Save moments ago and focus is on the status, and Signal K Admin raises its own alert on a failed request. Keep `labels.saved` for localization rather than runtime text. Blank outcome text is ignored.

`Disclosure` is the headless pair for button-triggered content that is not a heading section, such as an inline drawer. `useDisclosure` owns the ids, `aria-expanded`, `aria-controls`, and `hidden`, and hands focus to the panel (a region named by the trigger unless `aria-label` says otherwise) when opened through the trigger, and back to the trigger on close. A change made by setting `open` directly moves no focus into the panel, because nothing was pressed, but closing always returns focus to the trigger when the panel held it at that moment, whoever caused the change. That is what makes a Close button inside the panel, wired to the consumer's own setter, safe: without the handoff, hiding the panel takes its focused button away and leaves the reader on the body with no keyboard route back. A close while focus sits outside the panel still moves nothing. Spread its `triggerProps` and `panelProps` onto your own elements when the trigger is not a library `Button`. Both ids are generated unless `id` names the trigger or `idPrefix` names the pair (`<idPrefix>-trigger` and `<idPrefix>-panel`); reach for one where something outside the pair, such as a test harness or a deep link, has to name an element rather than hunt for it in the DOM. An id or prefix carrying whitespace throws, because `aria-controls` and `aria-labelledby` hold space separated lists.

`DisclosureTrigger` and `DisclosurePanel` normally read the `Disclosure` that wraps them, and either can take a `useDisclosure` result as `disclosure` instead. Reach for the prop where one context cannot serve: two drawers in the same row, with both triggers in a cluster and both panels below, would have to nest their providers, and the inner one would answer for both triggers. Call `useDisclosure` once per drawer, name each part's disclosure, and the composed panel replaces a hand-written `<section>` while keeping the ids, the region naming, `mountStrategy`, and the focus handoff. The prop wins where both are available, and a part with neither throws.

`Tabs` follows the ARIA tabs pattern without React Aria: one tab stop into the list, arrow keys move between enabled tabs (Left and Right for a horizontal list, reversed under `dir="rtl"`, Up and Down for a vertical one), Home and End jump to the ends, and each `TabPanel` is labeled by its `Tab` and is itself focusable. Under `activation="automatic"` (the default) arrow keys select as they move; under `"manual"` they only move focus and Enter or Space selects. `TabList` requires `aria-label` or `aria-labelledby`. A `badge` joins the tab's accessible name, so give a count badge a visible or hidden word ("2 errors") when the number alone would not read well. `TabPanel.focusable` drops the panel's own tab stop for a panel that is nothing but controls. `TabPanel` and `DisclosurePanel` share the `MountStrategy` type, where `"retain"` keeps a hidden subtree mounted with its effects paused and re-run on the next reveal, and `"unmount"` discards it. One known limitation: `Tabs` is generic over the consumer's value union, and a `TabList` built from a mapped array widens that union back to `string` unless the components are instantiated explicitly (`<Tab<Category> value="engine">`).

The value type is the consumer's own union: `onValueChange` reports it without a guard on the way back. It is pinned by a `value` or `defaultValue` of that type, or written out as `<Tabs<Category>>`; instantiate the children the same way (`<Tab<Category> value="engine">`) to have their values checked too. `TabsProps`, `TabProps`, and `TabPanelProps` written without a type argument still mean `string`. A `TabPanel` child may be a function, which the panel calls only where it renders it: pair it with `mountStrategy="unmount"` where the content is expensive to build, so an unselected tab builds nothing, and pass plain children everywhere else.

`Table` is a semantic `<table>` for a handful of rows: write `thead`, `tbody`, `tr`, `th`, and `td` as usual and use `TableHeaderCell` and `TableCell` where a column holds figures (`numeric` right-aligns and uses tabular numerals). It requires a name through `caption` (visible or hidden) or an ARIA attribute, and `zebra` paints alternate body rows with the stripe token. Wrap a wide table in `TableScrollRegion`, a focusable named region that scrolls sideways so keyboard users reach the overflow and the panel never scrolls horizontally. Reach for `DataGrid` when rows need sorting, selection, or virtualization. For an editable table, name each cell control with its column and its row, put `aria-invalid` and `aria-describedby` on the control rather than on the row, and leave the row a plain `tr`: a row is not a form field, and a message attached to it is announced at the wrong moment.

Exported types: `AccordionProps`, `CheckboxGroupProps`, `CheckboxGroupOption`, `CheckboxGroupLayout`, `DisclosureProps`, `DisclosureTriggerProps`, `DisclosurePanelProps`, `DisclosureContextValue`, `UseDisclosureOptions`, `UseDisclosureResult`, `EmptyStateProps`, `ProgressProps`, `ProgressTone`, `SaveActionBarProps`, `SaveActionBarLabels`, `SaveActionBarAction`, `SaveActionBarFocus`, `SaveActionBarFocusTarget`, `SaveActionBarOutcome`, `SaveActionBarState`, `SaveActionBarStateInput`, `TabsProps`, `TabsActivation`, `TabListProps`, `TabProps`, `TabPanelProps`, `TableProps`, `TableCaptionVisibility`, `TableHeaderCellProps`, `TableCellProps`, and `TableScrollRegionProps`.

Public values besides the components: `useDisclosure`, `resolveSaveActionBarState`, `toCheckboxGroupValue`, and `applyCheckboxGroupValue`.

## Data grid

`DataGrid` requires an accessible name, column children, `items`, and `renderRow`, and renders inside a `PanelRoot`, which supplies the scoped styles the grid installs on mount. Its package-specific options are `columns`, `density` (the shared `Density` union, `"default"` or `"compact"`), `caption`, `captionVisibility` (default `"visible"`), `emptyState`, `emptyTitle`, `emptyDescription`, selection state, controlled sorting state, `virtualize` (`"auto"` by default, or `"always"` or `"never"`), `virtualizeThreshold`, and `zebra`. Every DOM attribute the grid does not own reaches the container, so a grid can carry `aria-describedby`, `data-*`, or `hidden`. Dynamic `columns` must be an array: treat it as readonly and replace it when the column data changes, so React can replay StrictMode and concurrent renders safely. A value that is not an array throws, naming what it received. The default empty title is `"Nothing to show yet"`, with `emptyDescription` rendered under it, the default virtualization threshold is 100 rows, and the ref always resolves to the stable outer `HTMLDivElement`. `caption` gives a grid moving up from `Table` its visible name, and the grid points at it with `aria-labelledby` after any id the consumer supplied. A virtualized grid scrolls inside a bounded box: the package sets that bound through `--snui-data-grid-max-block-size` (default `60dvh`), and a consumer overrides it on the grid or the panel root. `--snui-data-grid-column-min` (default `6rem`) sets the column floor, and `--snui-table-cell-min` (default `6rem`) the cell floor inside `TableScrollRegion`; all three are consumer hooks read with a `var()` fallback rather than listed foundation tokens, as `--snui-sticky-clearance` is on a panel with a sticky `ActionBar`. Crossing the threshold under `"auto"` swaps one element tree for another and remounts the table, so a grid that grows, filters, or drains while it is on screen should pin `virtualize` to keep uncontrolled selection, focus, and scroll position. Selection shows as a leading bar plus a tint, because the tint alone sits at about 1.1:1 in Night; a panel wanting a per-row control renders its own. Under forced colors the selected row keeps the `Highlight` fill and rings in `HighlightText` while it holds keyboard focus, and a hovered row that is not selected takes a dashed `Highlight` outline instead, so moving the pointer across the grid never makes a row look selected. For any grid a user fills, pass `emptyState` with a description that says what the grid holds and an action that leads to the first row; the default title orients nobody and exists for prototypes and tests.

`Column` is the package's own wrapper around React Aria's Column and adds two column options that DataGrid applies to the header cell and to every cell in that column: `numeric` aligns the column to the end edge so figures line up (every body cell already uses tabular digits, which assumes Western Arabic digits: a panel pinned to a non-Latin numbering locale should format with `numberingSystem: "latn"` where column alignment matters), and `wrap` lets a virtualized cell wrap onto several lines. Set `wrap` on any text column whose value the operator must read in full, such as a Signal K path or a source name. Without `wrap`, a virtualized cell keeps one line, truncates with an ellipsis, and carries its text as a `title` when its content is only strings and numbers; a cell with element content is left to the consumer. A keyboard user still sees a truncated value whole: the cell holding keyboard focus drops its ellipsis and wraps while it holds focus. A touch user gets neither the `title` nor that reveal, which is why `wrap` is the setting for text columns. Non-virtualized cells always wrap, so `wrap` changes nothing below the threshold. `Row`, `Cell`, `Key`, `Selection`, `SortDescriptor`, and their related public types come from React Aria Components. The first column becomes the row header when the consumer does not mark one explicitly. Give each row a stable `id` or `key`. Sorting remains consumer controlled: update `items` when `onSortChange` reports a new descriptor.

React Aria keeps each rendered row against its item. `DataGrid` rebuilds the rows, including the cells a `Row` renders from a function, when `renderRow` changes identity or when the columns change: their ids, their count, or their `numeric`, `wrap`, and `width` options. The columns are compared by value, so a static header written afresh on every render costs nothing. Pass a stable `renderRow`: a module-level function, or a `useCallback` that lists every value it reads besides the item, such as the unit preference. An inline arrow rebuilds every rendered row whenever the panel renders, a cost a large or virtualized grid notices. A `Row`'s own `dependencies` still apply after the grid's.

Exported types: `DataGridProps`, `DataGridColumnProps`, `DataGridSelectionMode`, `DataGridCaptionVisibility`, `DataGridVirtualizeMode`, and, from React Aria Components, `CellProps`, `Key`, `RowProps`, `Selection`, `SortDescriptor`, and `SortDirection`. `DataGridColumnProps` is the package's column type; React Aria's own `ColumnProps` is not re-exported. Because those six types come from React Aria Components, a React Aria version change can change them with no change in this package, so a release that moves React Aria says so in its changelog.

The `dismissable` prop keeps that spelling; it is public API, and prose about the behavior may say "dismissible".

Use the library `Button` as a `Popover` trigger. A custom trigger must render a semantic interactive element, forward its ref to that element, and spread every injected event and ARIA prop onto it. A trigger that drops any part of that contract can break opening, focus return, keyboard use, or accessible naming. A library `Button` blocked with `ariaDisabled`, or loading, opens nothing.

Dialog dismissal has two switches: `dismissable` covers a press on the scrim and `keyboardDismissable` covers Escape. `AlertDialog` turns off scrim dismissal by default, so a stray click cannot discard a decision, and keeps Escape on, so a keyboard user can decline without tabbing to the cancel button. Every way the user declines (Escape, a scrim press, and the AlertDialog cancel button) calls `onCancel` once with the reason it took, `"escape"`, `"scrim"`, or `"cancel"`, and then `onOpenChange(false)`; closing through the `close` function handed to an `actions` render function, or changing a controlled `open`, does not. A `Dialog` with `dismissable={false}` and no actions leaves Escape as its only way out, which a touch screen reader user cannot send, so development warns about it whatever `keyboardDismissable` says; pass actions, or render a close control in the children. Both dialog warnings name the dialog by its title.

`Menu.triggerProps` takes the trigger button's own props, typed `MenuTriggerProps`: `iconOnly` for the square target an overflow menu's icon trigger takes, `ariaDisabled` with its `disabledReason` for a menu that cannot open yet, `loading`, `className`, a `ref`, `data-*` hooks, and the rest of a library `Button`. The words, the accessible name, the size, and the variant keep their own `Menu` props, and the menu owns the press, so those are left out. A blocked or loading trigger stays focusable and opens nothing, and an `aria-labelledby` in `triggerProps` names an otherwise unnamed trigger.

The `Menu` family forwards the DOM attributes React Aria passes through (`style`, `data-*`, `dir`, `lang`, `hidden`, `inert`, `translate`, and the global pointer, mouse, touch, wheel, scroll, animation, and transition events) and no others; `MenuElementAttributes` names the set. On `MenuItem` and `MenuSection` the `id` is the collection key rather than a DOM id, and `MenuSeparator` takes no `id` for the same reason; only `Menu` puts an `id` on its list. `MenuItem` derives its typeahead text from the strings inside its children, descending into elements and skipping hidden and `aria-hidden` ones; an item whose text comes from a component's own rendering, or an icon-only item, needs `textValue`, and an icon-only item needs an accessible name of its own as well. A `Menu` trigger whose label carries no text refuses to render without `triggerLabel`.

Exported types: `DialogProps`, `DialogActions`, `DialogWidth`, `AlertDialogProps`, `MenuProps`, `MenuItemProps`, `MenuItemTone`, `MenuSectionProps`, `MenuSeparatorProps`, `MenuTriggerProps`, `MenuElementAttributes`, `PopoverProps`, `PopoverWidth`, `OverlayOpenState`, `OverlayPlacement`, `ToastRegionProps`, `ToastContent`, `ToastQueue`, `ToastQueueOptions`, `ToastEviction`, `ToastEvictionReason`, `DialogCancelReason`, and `QueuedToast`.

`createToastQueue(options)` returns a queue with `enqueue`, `dismiss`, `clear`, `getSnapshot`, and `subscribe`, and takes an optional `onEvict` callback (a `ToastEviction` carrying the toast and a `ToastEvictionReason` of `"overflow"` or `"rejected"`; dismissals and clears are deliberate and are never reported). The exported `toast` queue covers the common single-region case. A queue holds at most five items. When full, it evicts the oldest toast that is neither focused nor more consequential than the arrival: an explicitly sticky toast (`duration: 0`) outranks a timed one, and a sticky warning or danger outranks both. When nothing in the queue may be dropped, the arrival itself is refused and reported through `onEvict` with reason `"rejected"`; `enqueue` still returns a key, which stays safe to pass to `dismiss`. One queue feeds exactly one region: a second region bound to the same queue renders, announces, and times out every toast a second time, which the package tolerates only across the moment a consumer swaps one region for another. Multiple regions with their own queues in one panel share a panel-contained, viewport-aware host while retaining independent labels and queues. Each toast's dismiss button is described by that toast's title, so a stack of notifications offers no two identically named controls. `ToastContent` requires `title` and accepts `description`, `tone`, `duration`, `live`, and `toneLabel`. `enqueue` throws synchronously when the title has no content, so a blank runtime message fails at the call site instead of inside the region. Duration defaults to 5,000 milliseconds for the info and success tones and to zero, a sticky toast, for warning and danger, because a failure that disappears cannot be re-read; set `duration` to time a warning or failure out on purpose. A `duration` no timer can wait out, a negative, `NaN`, `Infinity`, or more than 2,147,483,647 milliseconds, reads as zero.

A toast is spoken once, as text, and the cards are not live regions. The shared toast host mounts one polite and one assertive region, visually hidden, when the first `ToastRegion` mounts, before any toast arrives, and each toast adds one line to the region its `live` mode names: the tone name first, then the title and the description, as in "Information. Waypoints synced. 12 sent.". `live` defaults to assertive for danger and polite otherwise, and `"off"` shows a toast without speaking it. Lines are read in the order the toasts arrived, a toast arriving within 100 milliseconds of its region's creation waits for the region to exist, and a toast's line leaves when the toast leaves the queue. The card itself shows at once, and focus entering a card reads it once rather than twice. A test that finds toast text by role finds the host region, and a text match on a title also matches that line.

The notifications region is one Tab stop from the panel start, and F6 moves focus into it while a toast is showing; F6 is answered only while focus is inside the owning panel, so a second panel and the Signal K Admin chrome keep the key, and F6 and Shift+F6 both toggle. Dismissing a focused toast moves focus to the card that takes its slot, else to the newest remaining toast, else back to the element that had focus before entering the region, else to the panel root; focus never lands on the document body. Toasts stay visible, announced, and dismissable while a `Dialog` or `AlertDialog` is open.

Measure a polled status's liveness from the moment the browser received it, and use a Signal K `timestamp` only to say how old the source claims the value is: the server's clock and the browser's are independent on a boat, where a Raspberry Pi with no real-time clock takes GPS time once it has a fix. A watched path's `meta.timeout`, in fractional seconds, times 1,000 is the natural `staleAfterMs`. Saving a plugin's configuration restarts the plugin, so a panel polling a plugin route sees failures for that window; hold the last reachability state, or report it as not yet contacted, through the restart that follows the panel's own save rather than painting it as a danger "Unreachable".

## Localization defaults

Every package-owned user-visible string can be replaced by a prop, an option, or the panel's label bundle. Announcements owned by React Aria Components, such as `DataGrid` sort and selection announcements and the built-in strings of `Dialog`, `Menu`, `Popover`, and `Progress`, follow the browser locale instead; pin them by wrapping the panel in React Aria Components' `I18nProvider` from the consumer's own dependency. `RelativeAge` and `formatRelativeAge` render through `Intl.RelativeTimeFormat` for `options.locale`, falling back to the runtime locale when the tag is missing or malformed. Pin the wording by passing a locale in the options: `RELATIVE_AGE_EN` is the exported `{ locale: "en" }` for a panel whose surrounding copy is English anyway, and `PanelRoot.locale` publishes one locale for a panel to read with `usePanelLocale` and pass on. `LiveRegion` owns no strings; it announces whatever `message` the consumer passes. Every package default in the table below is a fixed English literal: the package reads no locale for its own copy, so a browser set to French or German shows locale-correct React Aria strings beside English package defaults until the panel replaces them. Signal K Admin itself is English only. `PanelRoot.locale` pins the formatters, not the strings.

Replace the defaults in one place with `PanelRoot.labels` or `PanelShell.labels`, which take a `PanelLabels` bundle: one optional group per surface, every key optional, published to every component in the panel and read back by a consumer component through `usePanelLabels`. Each string resolves as the component's own prop, then the bundle, then the package default, with blank text reading as absent at each step, so a call site can still say something more specific than the panel's wording and a partial translation leaves the rest in English. Two props are deliberate exceptions to the blank rule: a blank `ToastRegion label` and a blank `DataGrid emptyTitle` throw, because a blank written at the call site is a mistake, while a blank bundle entry for either falls back to the default. `PANEL_LABEL_DEFAULTS` exports the English defaults in the bundle's shape.

Two defaults deserve a deliberate override. The `danger` tone announces "Error", so pass `toneLabel` (for example "Caution") on a danger `Banner`, `Badge`, or sticky toast that warns about a destructive action rather than reporting a failure. `InlineConfirm` defaults to "Confirm" under "Confirm action", so set `title` to the question being asked and `confirmLabel` to the action verb ("Delete route") wherever the region reaches a user; the defaults are for tests and prototypes.

## Adoption status

Six NearlCrews Signal K panels consume this package. The names at least five of them import are the ones `fixtures/size/consumer-panel.ts` measures: `PanelShell`, `Section`, `CollapsibleSection`, `LabeledField`, `NumberField`, `TextInput`, `Select`, `Checkbox`, `Button`, `Banner`, `Text`, `Stack`, `Cluster`, `Badge`, `StatusIndicator`, `RelativeAge`, `useUnsavedChangesGuard`, and `SaveActionBar`. As of their 0.11.1 re-pin, no panel renders the `/data-grid` entry, `Menu`, `Popover`, the toast API (`ToastRegion`, `createToastQueue`, and `toast`), `AlertDialog`, `Accordion`, `RadioGroup`, `Switch`, `Progress`, the `Disclosure` components (`useDisclosure` alone is used), or `ThemeProvider`, and none imports the `/format` entry. Update this note at each consumer re-pin.

A new prop on a component no panel renders waits until two panels need it, the same evidence rule a new component meets. Fixes to shipped behavior are not held back: a defect in an unadopted component is still a defect in public API. The rule applies from 0.13.0. Two additions in that release predate it: `Switch` gained the description and error slots every other choice control has, and `Menu.triggerProps` closes the icon trigger's gap in the density contract's square target.
