# API reference

This reference summarizes the public `0.12.x` API. The TypeScript declarations shipped with the package are the canonical source for complete native HTML and React Aria prop types. This document focuses on package-specific props, defaults, entry points, ref targets, and user-visible strings.

Focused-entry-point APIs are not also exported from the package root, with one deliberate exception: `/format` republishes helpers the root also exports, because its whole purpose is reaching them without React in the graph. Consumers bundle each JavaScript entry point they import into their remote. Webpack consumers share only React and React DOM with the Signal K Admin host; Vite and other ESM consumers resolve the React entry points through the host-global shims instead. Every JavaScript entry declares a `default` condition pointing at the same target as its `import` (or, for `/federation`, its `require`) condition, so CommonJS tooling on Node 22.12 or newer can `require` it as well.

The stylesheet entry point has no React import or execution requirement. Installing the package still resolves the package's declared dependencies and React peer dependencies; `tokens.css` is an entry point, not a separate dependency-free package.

### Entry point sizes

The gzip size of each entry bundled alone, with React and React DOM external, as `node scripts/check-bundle-size.mjs --table` reports for the current release; the budget column is the ceiling that command enforces. A minimal panel that imports only the root entry adds about 40 KB gzip to its remote when bundled standalone; consumer remotes measure less after their own tree shaking, because the root entry carries React Aria's portal provider and the components a given panel never renders. Each component's CSS is reached only from that component, so a panel that renders no slider, switch, radio group, progress bar, tab list, table, or empty state ships none of their rules. Add the focused entries a panel imports to size its own ceiling, and expect the sum to overstate the result: each row is measured with every one of that entry's components live, and a focused entry carries the style modules of components a given panel never renders, plus install machinery the root entry already brought.

`PanelShell` is the frame every configuration panel repeats: it runs the `supportsNativeCssScope` preflight once at mount and renders `UnsupportedBrowserNotice` (or the `unsupported` element) when it fails, otherwise `PanelRoot`, an outer `Stack`, one polite and one assertive live region for the whole panel, the optional title at `headingLevel` (default 2, because Signal K Admin already renders the page heading and an `h5` card header, so a panel must not add an `h1`), the optional `description`, which renders with or without a title, the `ThemeToggle` where `themeToggle` places it, and a `PanelErrorBoundary` around the children. The two regions it mounts are what `usePanelAnnouncer` writes to, so a panel announces through a region that existed before the message. A titled shell also offers the level below its title to the `Section` and `CollapsibleSection` rendered inside it, so a panel titled at level 2 heads its sections at level 3 without being told; a shell with no title heads nothing and passes its own level through, an explicit `headingLevel` on a section still decides, and the derived level stops at 6. `themeToggle="between"` places the selector after the title block, so a panel with no title has nothing for it to sit between and takes the default `"end"` instead; leading the panel would hand the theme selector the panel's first tab stop, which no placement describes. A configuration panel states the placement rather than leaning on the default: `themeToggle="end"` is the convention the design contract records, and `themeToggle="none"` with a hand-placed `ThemeToggle` is the deliberate way out of it. On an unsupported browser the shell forwards its `className`, `id`, and other attributes to the notice, whose title and body come from `unsupportedLabels`; the panel `ref` is not forwarded there, because that branch renders a section rather than the panel div. `PanelErrorBoundary` catches a render error inside the panel and offers "Try again", which clears the error and renders the children again, plus a reload action, which `PanelShell` offers by default and `onReload={null}` withholds. The default fallback is not an assertive alert: it takes focus when the crash left the page with nothing focused, and otherwise announces through the panel announcer. The boundary records every caught error with `console.error`, including the component stack, as well as calling `onError`. Render it inside `PanelRoot` so the fallback is styled.

`CollapsibleSection.leading` renders before the heading and outside the toggle button, so an enable checkbox keeps its own semantics and hit area. `variant="embedded"` drops the border, radius, and shadow for a section nested inside a `Card`. `landmark={false}` removes the region naming; `Accordion` applies that default to its children, because six regions from one accordion would crowd the landmark list, and a child can pass `landmark` to opt back in.

`InlineConfirm.busy` blocks Confirm while the confirmed action runs. It does not close the region's escape path: Cancel stays enabled and Escape keeps dismissing, because a user declining an action is not in conflict with work already under way, and a keyboard user must always be able to leave. So `onCancel` can fire while `busy` is true, with reason `"cancel"` or `"escape"`, and the consumer decides whether that aborts the work, closes the region, or both. `busy` takes effect only on a controlled region: an uncontrolled one closes itself on Confirm, so there is nothing left on screen to block. `onOpenChange` reports every close in one place.

`statusRef`, `initialFocusRef`, `returnFocusRef`, and `dismissFocusRef` are focus destinations. They are not aliases for a component's own `ref`. `Banner.dismissFocusRef` serves every way the banner takes focus away, not the Dismiss press alone: an action in `actions` that unmounts the banner, and an announcing banner whose actions go with its message, both hand focus to the same destination. The banner moves focus only when it held it, and the move is synchronous, so a panel that focuses whatever it renders in the banner's place keeps that focus. `ActionBar` makes its status destination programmatically focusable but does not move focus automatically; the consumer calls `statusRef.current?.focus()` after the initiating control disappears or becomes unavailable. A viewport-bottom bar scrolls a focused panel control clear when focus moves or a viewport resize docks the bar, preserving focus-ring clearance through nested scroll containers. It never scrolls while a pointer is pressed, so a press on a control the bar overlaps keeps its click, and a clearance skipped for that reason is not replayed afterward: a pointer user can see the control they pressed, and a later scroll would move content under a pointer that may still be there. Keyboard and programmatic focus clear immediately.

#### CollapsibleSection mountStrategy and effects

`mountStrategy` decides what happens to hidden content, and the two retaining values have consequences a consumer must design for.

- `"retain"`, the default, and `"lazy-retain"` keep hidden content mounted inside React `Activity`. State and `useRef` values survive a collapse, and so does uncontrolled DOM value state. Every effect and layout effect in that subtree runs its cleanup when the section collapses, refs detach, and all of them run again when it reopens.
- `"unmount"` removes hidden content. Effects unmount for real and state is discarded, so nothing survives a collapse.

The consequence that surprises consumers is that an effect with an empty dependency list is not a run-once effect under a retaining strategy. It runs once per expand, against state that survived from the previous expand. Guard genuinely one-time work with a `useRef` flag, which survives the collapse with the state it protects.

Two failure shapes follow from the same rule, both observed in consumer panels:

- A field that reports validity from an effect, and clears that report in the effect's cleanup, silently drops its invalid state when the section collapses. Re-running the effect on expand then reinitializes the field from props and discards an edit the user had in progress, because the edit survived but the effect treated the expand as a fresh mount.
- A request that starts in an effect and aborts in that effect's cleanup is aborted when the section collapses, so the completion path that would clear a busy flag never runs and a control stays `aria-busy` forever.

Keep each cleanup symmetric with its own setup: unsubscribe what the effect subscribed, and do not use a cleanup to mutate reported validity, busy state, or other state that must outlive the hidden period. Initialize from props only behind a ref guard. An effect-registered listener also observes nothing while the section is collapsed, so a subtree that must see events during that time, a form reset for example, belongs outside the collapsible or in a consumer-owned store. Choose `"unmount"` when a subtree cannot tolerate paused effects and its state is disposable, and keep a retaining strategy when the state must survive.

`TextInput` accepts `date`, `datetime-local`, `email`, `month`, `password`, `search`, `tel`, `text`, `time`, `url`, and `week`. `Textarea` keeps the HTML element's casing rather than `TextArea`. `monospace` renders a text control in the panel's monospace stack for keys, paths, and identifiers; `Textarea.minRows` sets the visible row floor in place of the default minimum height and, where the browser sizes fields from content, lets the control grow from that floor. `Button` makes empty, dangerous, and unknown anchor schemes inert while keeping `role="link"`, and logs one development warning per rejected `href`. HTTP, HTTPS, mail, telephone, fragment, query, and relative destinations remain active.

`Button.ariaDisabled`, when set, decides whether activation is blocked and a native `aria-disabled` attribute is ignored; when it is omitted the native attribute is read. A natively `disabled` button never also carries `aria-disabled`: the two are exclusive, and `disabled` wins.

`Checkbox.ariaDisabled` follows the same rule and applies it to a value rather than an action. Reach for it where the box cannot change right now but its value is real, such as the last remaining selection in a list: `disabled` takes the box out of the tab order, so setting it on the box the user is standing on destroys their focus and drops them on the body. A blocked box stays focusable, keeps its checked and mixed states, and still submits with its form, while the change is refused from the box, from the label, and from the Space key alike. `Enter` is left alone, because it belongs to the surrounding form rather than to the box. `CheckboxGroup` takes the same flag per option, and select-all leaves blocked options as it finds them, since an option the user cannot change is not one select-all may change for them. `Switch` and `RadioGroup` express this as `readOnly`, which React Aria implements: the control keeps its tab stop and refuses the change. Reach for `disabled` on any of them only when the control is genuinely unavailable, where giving up the tab stop is part of what you are saying.

An intrinsic `LabeledField` child must be a labelable `button`, non-hidden `input`, `meter`, `output`, `progress`, `select`, or `textarea`. Use the render-prop form for a composite control. Children must forward `id`, `required`, `disabled`, `name`, `aria-describedby`, `aria-errormessage`, and `aria-invalid`. `FieldControlProps` and `LabeledFieldControlProps` name this contract. The render-prop argument also carries `descriptionId` and `errorId`, which are lookups rather than attributes: pass it through `splitLabeledFieldControlProps(props)` to receive `{ controlProps, descriptionId, errorId }`, spread `controlProps` onto the control, and point secondary controls at the ids with `aria-describedby`. Where text outside the field also describes the control, name it in `controlDescribedBy`, which takes one id or a list: the field reads its own description and error first and those ids after, and both the element-child and the render-prop form receive one merged `aria-describedby`, so no caller writes the join.

`NumberField` keeps the text the user is typing in a draft and commits numbers. Without `fallback` it validates: an empty, unparsable, fractional (under `integer`), or out-of-range draft shows a message, sets `aria-invalid`, reports `onValidityChange(false)`, and commits nothing until the user fixes it; `exclusiveMin` and `exclusiveMax` make the bound itself invalid, and `step` reaches the input for its spinner without being enforced, so a half-typed value is never rejected mid-edit. With `fallback` it clamps: empty or unparsable input commits the fallback, fractions truncate, values snap to `step`, and out-of-range values clamp to the nearest bound, so every keystroke commits a number. `allowEmpty` widens `value` and `onValueChange` to admit `undefined` for a cleared field. Blur and Enter finish an edit (an invalid draft stays visible with its message), a wheel over the focused input blurs it so scrolling cannot spin the value, and the draft survives a retaining `CollapsibleSection` collapse. `onValidityChange` fires on transitions only and never from an unmount, so a consumer that stops rendering a field clears its own entry. `useNumberDraft(value, onValueChange, options)` exposes the same behavior for a bare `NumberInput`, and `resolveNumberDraft(raw, options)` is the pure resolution step, which reads only the notation an `<input type="number">` can produce. `NumberField.unit` is a label, not a conversion: source the unit string, and any conversion behind it, from the consumer's own resolution of the server unit preferences, which the package boundary leaves with the plugin.

Every control and group takes its accessible name from `label`: `Checkbox`, `Switch`, `Radio`, `RadioGroup`, `SegmentedControl`, `ThemeToggle`, and `NumberField` through `LabeledField`. `Switch` and `Radio` also accept children as the label. `FieldGroup` and `CheckboxGroup` take `legend` because they render a real `<legend>`; `SegmentedControl` and `ThemeToggle` render a `role="radiogroup"` div, so they take `label`, and `FieldGroup` accepts `label` beside `legend` for the same reason a consumer reaches for one word everywhere. The rule for a label's type follows from what the label becomes: plain text where the value turns into an accessible name, `ReactNode` where it is only rendered, and both on `Menu`, whose trigger derives a name from its content when `triggerLabel` is absent. `Checkbox.labelVisibility="hidden"` keeps the required label in the accessible name while removing it from the layout, for a select-all box in a table header or a toggle in a dense row. `SwitchProps` and `RadioProps` are unions over the naming pair: omitting both `label` and children is a type error, while a present but blank value still throws at render. `SegmentedControlProps` is no longer such a union, because `label` is now its only naming prop and is required.

Change handlers split along one rule. Native wrappers (`TextInput`, `NumberInput`, `RangeInput`, `Select`, `Textarea`, and `Checkbox`) take React change events through `onChange`. Composed controls report values with a callback named for the payload: `Switch.onCheckedChange(checked)`, `RadioGroup.onValueChange(value)`, `SegmentedControl.onValueChange(value)`, `ThemeToggle.onValueChange(theme)`, `CheckboxGroup.onValueChange(values)`, and `NumberField.onValueChange(value)`. The `onChange` value aliases those four controls carried are removed.

`SegmentedControl.options` must contain at least one option. Every option needs a non-empty label, and option values must be unique. All four arrow keys move within the group in either orientation, the horizontal pair mirroring in a right-to-left panel, Home and End reach the ends, and holding Ctrl, or Command on macOS, moves focus without changing the selection. `readOnly` and a per-option `ariaDisabled` refuse the change through `aria-disabled` rather than the native attribute, so the option the operator is standing on keeps its focus.

Every tone-badged component (`Badge`, `Metric`, `Banner`, `StatusIndicator`, `Card`) renders the same glyph and visually hidden announcement for a semantic tone, so the state never depends on color alone. A blank `toneLabel` falls back to the default tone name on every one of them, and a `toneLabel` on `tone="neutral"` is ignored everywhere, because neutral carries no meaning to announce. `StatusIndicator` shows the glyph beside its shaped dot, and `size="compact"` keeps only the dot and glyph visible while the text stays in the accessibility tree. A `Card` with a semantic `tone` paints the Banner accent bar and places the glyph in its header; give a toned card a header so the glyph has a home. Night collapses the tone colors onto one red-capped hue, so a `Progress.tone` or a `Text.tone` there reads as emphasis rather than as a particular tone: state the meaning in words wherever it matters. A `Badge` is a label, not a control; a count the operator can act on belongs in a compact `Button`, in the danger variant when the action is destructive.

`live` on `Banner`, `StatusIndicator`, and `Metric` makes the component announce its own updates, and a live region has to exist before its first message or a screen reader does not observe it. So render the component wherever the panel can produce a message and let its content go empty: `<Banner live="polite">{message}</Banner>`, not `{message && <Banner live="polite">{message}</Banner>}`, which builds the region and its first message in the same commit. With `live` set, or a live `role` given to `Banner` or `StatusIndicator`, and nothing to show, the component renders the element that carries the role empty, with no tone glyph, no dot, and no unit, and the stylesheet takes that empty element out of the flow: it reserves no box, border, padding, or margin, so a waiting region is invisible. A `Banner` carrying `actions` or `onDismiss` always renders in full, because hiding a focusable control would strand it. The same rule governs the field error regions and `LiveRegion` below. `live` defaults to `"off"` on `Banner`, `StatusIndicator`, and `Metric`, and to `"polite"` on `LiveRegion`, whose whole job is announcing. A role that announces by itself, `alert`, `log`, or `status`, suppresses `aria-live` so nothing double speaks; any other role, a landmark or a grouping, keeps the mode the caller asked for.

`LiveRegion` is a visually hidden announcer for state changes no visible control owns, such as a scan result count. Render it before the first message and update `message`; screen readers only observe a region that already existed. Setting `message` to the words the region already carries changes nothing in the DOM and is therefore silent, so pass an `announceKey` that differs per announcement (a press count, or the id of the event behind it): the region empties itself for a tenth of a second and restores the text, which is the change a screen reader reads. Callers pass plain text and never an invisible character. `RelativeAge` renders an age as words: pass `since` for a live age the component keeps current (it ticks every `tickMs`, stamps a `<time dateTime>` from the timestamp, and reads the clock once at mount and then only on its tick, never on a re-render). Every age sharing a `tickMs` shares one timer and refreshes at the same instants, so a panel full of ages costs one wake-up per interval. Pass `ageMs` instead for a value the consumer already computed. Prefer the component wherever the result is rendered rather than concatenated: `.snui-relative-age` carries tabular numerals, so `<RelativeAge ageMs={n} options={RELATIVE_AGE_NARROW} />` holds its width as the digits change, while the bare string `formatRelativeAge` returns carries no class and reflows on every tick. `announceKey` on `Banner` and `StatusIndicator` works the same way as it does here.

In normal component use, `ThemeToggle` renders inside `PanelRoot`. An advanced integration may supply the exported `ThemeProvider` directly and read the current choice with `usePanelTheme`, but that provider does not install component styles or create an overlay portal root. Both `ThemeProvider` and `PanelRoot` take `defaultTheme`, the choice a document with no stored preference starts on; there is no controlled `theme` prop, because the preference is one document-wide value. `UnsupportedBrowserNotice` is intentionally standalone so a consumer can render it after a failed browser preflight without first mounting `PanelRoot`; `PanelShell` does that for you. The notice is a plain section named by its heading, not a live region: it is present at first render, so there is nothing to interrupt. It carries `data-snui-unsupported` and `data-browser-compatibility-message` on its root, the two public hooks a host or a browser test selects it by, and it joins a consumer `aria-labelledby` with its own heading rather than replacing it.

The first `Accordion` child with `defaultOpen` wins. Keep child order static because coordinated state is positional. Omitting `Progress.value`, or passing a non-finite value such as the `NaN` a division by zero produces, creates an indeterminate indicator. `EmptyState.title` is a styled div, so the consumer owns the surrounding heading outline.

`CheckboxGroup` renders one `Checkbox` per option inside a `FieldGroup` and reports the selected values in option order. `name` goes onto every checkbox, so native form data lists the selection. `selectAllLabel` adds a tri-state select-all checkbox to the legend row that completes a partial selection and clears a full one while leaving disabled options alone. `emptyWarning` mounts an announcing status region and fills it, with the warning tone shape and label, while nothing is selected; `emptyWarningLive` chooses how it announces and defaults to polite, and the fieldset is described by it only while it shows. `selectAllLabel` has no default, because the wording names the things being selected; the house form is "All <things>". `toCheckboxGroupValue` and `applyCheckboxGroupValue` convert between the selection array and the record of booleans a plugin schema stores, and a selected value with no matching option is dropped on the next toggle. `SaveActionBar` is the Save and Discard footer of a configuration panel with its status line. State stays with the consumer; the component owns presentation and focus. Save is enabled while there is something to save (edits, or a plugin that has never been configured) and blocked by `invalidMessage` or `saving`; the status is a polite `StatusIndicator` whose tone follows the state, including a validation message, so the region keeps one stable role rather than gaining it in the same commit that writes the text. After either action, focus moves to the status, because the pressed button usually disables itself; `focusOnAction="none"` leaves focus alone for a panel that sends it to the field it refused. A save the bar has to refuse is blocked through `aria-disabled` and a description rather than the native `disabled` attribute, so Save and Discard keep their place in the tab order and say why; `SaveActionBarState.blocked` reports that state to a consumer deriving it. `resolveSaveActionBarState` exposes the same rules as data. Pair the bar with `useUnsavedChangesGuard(dirty)`, which asks the browser to confirm unloading while `dirty` is true.

`Disclosure` is the headless pair for button-triggered content that is not a heading section, such as an inline drawer. `useDisclosure` owns the ids, `aria-expanded`, `aria-controls`, and `hidden`, and hands focus to the panel (a region named by the trigger unless `aria-label` says otherwise) when opened through the trigger, and back to the trigger on close. A change made by setting `open` directly moves no focus into the panel, because nothing was pressed, but closing always returns focus to the trigger when the panel held it at that moment, whoever caused the change. That is what makes a Close button inside the panel, wired to the consumer's own setter, safe: without the handoff, hiding the panel takes its focused button away and leaves the reader on the body with no keyboard route back. A close while focus sits outside the panel still moves nothing. Spread its `triggerProps` and `panelProps` onto your own elements when the trigger is not a library `Button`. Both ids are generated unless `id` names the trigger or `idPrefix` names the pair (`<idPrefix>-trigger` and `<idPrefix>-panel`); reach for one where something outside the pair, such as a test harness or a deep link, has to name an element rather than hunt for it in the DOM. An id or prefix carrying whitespace throws, because `aria-controls` and `aria-labelledby` hold space separated lists.

`DisclosureTrigger` and `DisclosurePanel` normally read the `Disclosure` that wraps them, and either can take a `useDisclosure` result as `disclosure` instead. Reach for the prop where one context cannot serve: two drawers in the same row, with both triggers in a cluster and both panels below, would have to nest their providers, and the inner one would answer for both triggers. Call `useDisclosure` once per drawer, name each part's disclosure, and the composed panel replaces a hand-written `<section>` while keeping the ids, the region naming, `mountStrategy`, and the focus handoff. The prop wins where both are available, and a part with neither throws.

`Tabs` follows the ARIA tabs pattern without React Aria: one tab stop into the list, arrow keys move between enabled tabs (Left and Right for a horizontal list, reversed under `dir="rtl"`, Up and Down for a vertical one), Home and End jump to the ends, and each `TabPanel` is labeled by its `Tab` and is itself focusable. Under `activation="automatic"` (the default) arrow keys select as they move; under `"manual"` they only move focus and Enter or Space selects. `TabList` requires `aria-label` or `aria-labelledby`. A `badge` joins the tab's accessible name, so give a count badge a visible or hidden word ("2 errors") when the number alone would not read well. `TabPanel.focusable` drops the panel's own tab stop for a panel that is nothing but controls. `TabPanel` and `DisclosurePanel` share the `MountStrategy` type, where `"retain"` keeps a hidden subtree mounted with its effects paused and re-run on the next reveal, and `"unmount"` discards it. One known limitation: `Tabs` is generic over the consumer's value union, and a `TabList` built from a mapped array widens that union back to `string` unless the components are instantiated explicitly (`<Tab<Category> value="engine">`).

The value type is the consumer's own union: `onValueChange` reports it without a guard on the way back. It is pinned by a `value` or `defaultValue` of that type, or written out as `<Tabs<Category>>`; instantiate the children the same way (`<Tab<Category> value="engine">`) to have their values checked too. `TabsProps`, `TabProps`, and `TabPanelProps` written without a type argument still mean `string`. A `TabPanel` child may be a function, which the panel calls only where it renders it: pair it with `mountStrategy="unmount"` where the content is expensive to build, so an unselected tab builds nothing, and pass plain children everywhere else.

`Table` is a semantic `<table>` for a handful of rows: write `thead`, `tbody`, `tr`, `th`, and `td` as usual and use `TableHeaderCell` and `TableCell` where a column holds figures (`numeric` right-aligns and uses tabular numerals). It requires a name through `caption` (visible or hidden) or an ARIA attribute, and `zebra` paints alternate body rows with the stripe token. Wrap a wide table in `TableScrollRegion`, a focusable named region that scrolls sideways so keyboard users reach the overflow and the panel never scrolls horizontally. Reach for `DataGrid` when rows need sorting, selection, or virtualization. For an editable table, name each cell control with its column and its row, put `aria-invalid` and `aria-describedby` on the control rather than on the row, and leave the row a plain `tr`: a row is not a form field, and a message attached to it is announced at the wrong moment.

## Data grid

`DataGrid` requires an accessible name, column children, `items`, and `renderRow`, and renders inside a `PanelRoot`, which supplies the scoped styles the grid installs on mount. Its package-specific options are `columns`, `density` (the shared `Density` union, `"default"` or `"compact"`), `caption`, `captionVisibility` (default `"visible"`), `emptyState`, `emptyTitle`, `emptyDescription`, selection state, controlled sorting state, `virtualize` (`"auto"` by default, or `"always"` or `"never"`), `virtualizeThreshold`, and `zebra`. Every DOM attribute the grid does not own reaches the container, so a grid can carry `aria-describedby`, `data-*`, or `hidden`. Dynamic `columns` must be a readonly array so React can replay StrictMode and concurrent renders safely; replace the array when the column data changes. The default empty title is `"Nothing to show yet"`, with `emptyDescription` rendered under it, the default virtualization threshold is 100 rows, and the ref always resolves to the stable outer `HTMLDivElement`. `caption` gives a grid moving up from `Table` its visible name, and the grid points at it with `aria-labelledby` after any id the consumer supplied. A virtualized grid scrolls inside a bounded box: the package sets that bound through `--snui-data-grid-max-block-size` (default `60dvh`), and a consumer overrides it on the grid or the panel root. `--snui-data-grid-column-min` (default `6rem`) sets the column floor, and `--snui-table-cell-min` (default `6rem`) the cell floor inside `TableScrollRegion`; all three are consumer hooks read with a `var()` fallback rather than listed foundation tokens, as `--snui-sticky-clearance` is on a panel with a sticky `ActionBar`. Crossing the threshold under `"auto"` swaps one element tree for another and remounts the table, so a grid that grows, filters, or drains while it is on screen should pin `virtualize` to keep uncontrolled selection, focus, and scroll position. Selection shows as a leading bar plus a tint, because the tint alone sits at about 1.1:1 in Night; a panel wanting a per-row control renders its own. For any grid a user fills, pass `emptyState` with a description that says what the grid holds and an action that leads to the first row; the default title orients nobody and exists for prototypes and tests.

`Column` is the package's own wrapper around React Aria's Column and adds two column options that DataGrid applies to the header cell and to every cell in that column: `numeric` aligns the column to the end edge so figures line up (every body cell already uses tabular digits, which assumes Western Arabic digits: a panel pinned to a non-Latin numbering locale should format with `numberingSystem: "latn"` where column alignment matters), and `wrap` lets a virtualized cell wrap onto several lines. Set `wrap` on any column whose value the operator must read in full, because the truncation `title` needs a pointer to reach. Without `wrap`, a virtualized cell keeps one line, truncates with an ellipsis, and carries its text as a `title` when its content is only strings and numbers; a cell with element content is left to the consumer. Non-virtualized cells always wrap, so `wrap` changes nothing below the threshold. `Row`, `Cell`, `Key`, `Selection`, `SortDescriptor`, and their related public types come from React Aria Components. The first column becomes the row header when the consumer does not mark one explicitly. Give each row a stable `id` or `key`. Sorting remains consumer controlled: update `items` when `onSortChange` reports a new descriptor.

Exported types: `DataGridProps`, `DataGridColumnProps`, `DataGridSelectionMode`, `DataGridCaptionVisibility`, `DataGridVirtualizeMode`, and, from React Aria Components, `CellProps`, `Key`, `RowProps`, `Selection`, `SortDescriptor`, and `SortDirection`. `DataGridColumnProps` is the package's column type; React Aria's own `ColumnProps` is not re-exported.

Use the library `Button` as a `Popover` trigger. A custom trigger must render a semantic interactive element, forward its ref to that element, and spread every injected event and ARIA prop onto it. A trigger that drops any part of that contract can break opening, focus return, keyboard use, or accessible naming.

Dialog dismissal has two switches: `dismissable` covers a press on the scrim and `keyboardDismissable` covers Escape. `AlertDialog` turns off scrim dismissal by default, so a stray click cannot discard a decision, and keeps Escape on, so a keyboard user can decline without tabbing to the cancel button. `createToastQueue(options)` returns a queue with `enqueue`, `dismiss`, `clear`, `getSnapshot`, and `subscribe`, and takes an optional `onEvict` callback (a `ToastEviction` carrying the toast and a `ToastEvictionReason` of `"overflow"` or `"rejected"`; dismissals and clears are deliberate and are never reported). The exported `toast` queue covers the common single-region case. A queue holds at most five items. When full, it evicts the oldest toast that is neither focused nor more consequential than the arrival: an explicitly sticky toast (`duration: 0`) outranks a timed one, and a sticky warning or danger outranks both. When nothing in the queue may be dropped, the arrival itself is refused and reported through `onEvict` with reason `"rejected"`; `enqueue` still returns a key, which stays safe to pass to `dismiss`. One queue feeds exactly one region: a second region bound to the same queue renders, announces, and times out every toast a second time, which the package tolerates only across the moment a consumer swaps one region for another. Multiple regions with their own queues in one panel share a panel-contained, viewport-aware host while retaining independent labels and queues. Each toast's dismiss button is described by that toast's title, so a stack of notifications offers no two identically named controls. `ToastContent` requires `title` and accepts `description`, `tone`, `duration`, `live`, and `toneLabel`. `enqueue` throws synchronously when the title has no content, so a blank runtime message fails at the call site instead of inside the region. Duration defaults to 5,000 milliseconds for the info and success tones and to zero, a sticky toast, for warning and danger, because a failure that disappears cannot be re-read; set `duration` to time a warning or failure out on purpose. Announcements default to assertive for danger and polite otherwise.

The notifications region is one Tab stop from the panel start, and F6 moves focus into it while a toast is showing; F6 is answered only while focus is inside the owning panel, so a second panel and the Signal K Admin chrome keep the key, and F6 and Shift+F6 both toggle. Dismissing a focused toast moves focus to the card that takes its slot, else to the newest remaining toast, else back to the element that had focus before entering the region, else to the panel root; focus never lands on the document body. Toasts stay visible, announced, and dismissable while a `Dialog` or `AlertDialog` is open.

## Localization defaults

Every package-owned user-visible string can be replaced by a prop or option. Announcements owned by React Aria Components, such as `DataGrid` sort and selection announcements and the built-in strings of `Dialog`, `Menu`, `Popover`, and `Progress`, follow the browser locale instead; pin them by wrapping the panel in React Aria Components' `I18nProvider` from the consumer's own dependency. `RelativeAge` and `formatRelativeAge` render through `Intl.RelativeTimeFormat` for `options.locale`, falling back to the runtime locale when the tag is missing or malformed. Pin the wording by passing a locale in the options: `RELATIVE_AGE_EN` is the exported `{ locale: "en" }` for a panel whose surrounding copy is English anyway, and `PanelRoot.locale` publishes one locale for a panel to read with `usePanelLocale` and pass on. `LiveRegion` owns no strings; it announces whatever `message` the consumer passes. Every package default in the table below is a fixed English literal: the package reads no locale for its own copy, so a French or German Admin shows locale-correct React Aria strings beside English package defaults until the panel replaces them. Replace them in one place with `PanelRoot.labels` or `PanelShell.labels`, which take a `PanelLabels` bundle: one optional group per surface below, every key optional, published to every component in the panel and read back by a consumer component through `usePanelLabels`. Each string resolves as the component's own prop, then the bundle, then the package default, with blank text reading as absent at each step, so a call site can still say something more specific than the panel's wording and a partial translation leaves the rest in English. Two surfaces stay outside the bundle: the compatibility notice renders before the panel exists and takes `PanelShell.unsupportedLabels`, and `CheckboxGroup.selectAllLabel` names the things being selected rather than package wording. `PanelRoot.locale` pins the formatters, not the strings.

Two defaults deserve a deliberate override. The `danger` tone announces "Error", so pass `toneLabel` (for example "Caution") on a danger `Banner`, `Badge`, or sticky toast that warns about a destructive action rather than reporting a failure. `InlineConfirm` defaults to "Confirm" under "Confirm action", so set `title` to the question being asked and `confirmLabel` to the action verb ("Delete route") wherever the region reaches a user; the defaults are for tests and prototypes.

## CSS contract
